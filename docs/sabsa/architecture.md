### How — Process

**Which business processes depend on security, and how?**

The value-creating processes that depend on security are the product's own build, test, release and disclosure lifecycle. Building and testing: every change runs the enforced quality gates (compile, unit tests, PMD, SpotBugs, JaCoCo coverage floors, PIT mutation floors, dependency-check on CVSS≥7.0, license allowlist, CycloneDX SBOM) and the ArchUnit plugin-seam invariants — trust properties verified mechanically on every build, not merely documented. Releasing: distribution integrity depends on the supply-chain invariants (for example, the ANTLR grammar-compiler JARs excluded from `lib/`), on GitHub's per-asset SHA-256 digests, and on attestation manifests and reproducibility receipts. Disclosing: the coordinated vulnerability disclosure process (private GitHub advisory or PGP email) operated to published response SLAs. Each process is a point where integrity, authenticity and reproducibility are critical to the product earning the trust its regulated audience requires; a failure in any of them would directly undermine the output's standing as evidence.

**Where does the business operate: locations, jurisdictions, markets?**

### When — Time

**When: which business cycles, deadlines and time dependencies constrain security?**

The binding time dependencies are: the per-change / per-build cycle, where every commit must pass the enforced gates before it is accepted; the per-release cycle, where checksums, attestation manifests and reproducibility receipts are produced for the shipped distribution; and the coordinated-disclosure clock, with published response SLAs of acknowledge within 2 business days, triage within 5, and a fix or mitigation plan within 30 days (critical/high) or 90 days (lower). Downstream, the product's output feeds customers' periodic audit and resilience-testing cycles (for example DORA's regularly-repeated testing, with coverage not regressed between periods), so reproducibility must hold across those intervals. There is no fixed calendar release cadence in the material; releases are event-driven — triggered by change and by disclosure.

### How — Process

**How: which security strategies and architectural layering will meet the objectives?**

The strategy is assurance by construction rather than by perimeter, resting on four load-bearing ideas. (1) A determinism contract that cleanly separates deterministic AST discovery from non-deterministic AI, and constrains the AI to a closed, versioned taxonomy and an explicit method list so it can neither invent nor omit methods. (2) Frozen, versioned contracts for the taxonomy and the audit/evidence schemas, so that any change is deliberate and visible. (3) Mechanically enforced quality and supply-chain gates on every build, which turn trust properties into testable facts rather than claims. (4) A deliberately proportionate trust basis — GitHub's per-asset SHA-256 digests, content hashes, reproducibility receipts and the scanner-script integrity check give tamper-evidence and verifiability, but per owner decision D-1 the project does not adopt managed-key release signing, and states that boundary (integrity, not proof of origin) explicitly. No separate strategy (SG) elements are built; this approach is synthesised from the drivers and attributes and realised through the logical services.

## 6. Logical layer — Designer's view

This layer describes the security services, policies, information and entities that deliver the concept.

### What — Assets

**What information needs protecting, and how is it classified?**

The information to protect, and the one boundary that classifies it, is the data-governance rule on what may leave the scan host. Everything structural is always local — no network under any configuration: source traversal, parsing, method discovery, content-hash computation, CSV/SARIF output, cache read/write, override-file read and delta compare. When, and only when, `-ai` is used with a non-local provider, exactly three things are submitted per test class: (1) the taxonomy text (configuration, no project content); (2) the discovered test-method names and line numbers, which prevent invent/omit; and (3) the single test-class source file, truncated to `-ai-max-class-chars`. Never submitted: production source, build scripts, config files, credentials or secrets, DB schemas, infra definitions, other test files, or file paths and directory structure. This minimal egress set is the classified information flow the architecture governs; everything outside it is classified as never-transmitted.

The CI/build domain associates with the distribution channel at release, bound by GitHub's per-asset SHA-256 digests. The data-residency tiers are the configurable form of the scan-host-to-provider association.

### When — Time

**When: what is the security processing cycle?**

Security processing is tied to three cycles. Per-change: every commit updates README, docs and Javadoc with the code and must satisfy the static-analysis and schema-stability rules. ### When — Time

**When: in what order and at what times do the controls execute?**

The control sequence at run time is: at startup each discovery plugin computes the SHA-256 of its helper scanner script and compares it to the `MANIFEST.MF` build-time hash, aborting before any method is produced on a mismatch; only then does structural discovery run (traverse, parse, discover, content-hash, emit); optional AI classification follows, bounded to the taxonomy and the discovered method set, with cache and override consulted first so unchanged classes are not re-sent. ## Annex C. Governance, policy and trust register

### Security strategies

### Architecture decisions
- **AD-001 Hashes yes, managed-key signing no (D-1)** — MethodAtlas relies on published SHA-256 hashes (GitHub's automatic per-asset digest) and keyless build provenance for release integrity, and deliberately does NOT use managed-key cryptographic signing of release packages. Scope boundary: this governs the project's own releases only; the product's `-attest` and `-evidence-pack` features let consumers sign their own evidence and are unaffected.; rationale: Managed-key signing would require key management, rotation and administration not justified for an application of this size (owner decision D-1). Keyless SLSA provenance (D-4) was later admitted because it carries no long-lived keys. The residual — whole-JAR repackaging / channel substitution not cryptographically prevented, and OpenSSF Signed-Releases unmet — is accepted and documented (EX-001).; owner: the Architect and Programmer.
- **AD-002 Deterministic structural layer, bounded AI layer** — AST-based discovery is fully deterministic and never depends on AI; the AI layer is confined to a closed, versioned taxonomy and an explicit list of discovered methods, so it can neither invent nor omit a method. The two layers are kept strictly separate.; rationale: Regulated adopters need output that is traceable, repeatable and defensible. Determinism makes the structural record re-checkable; bounding the AI turns a non-deterministic component into an auditable one. The separation is enforced at build time by ArchUnit (SC-003).; owner: the Architect and Programmer.
- **AD-003 ServiceLoader plugin-seam boundary** — Language support is provided by independent discovery plugins resolved at runtime through ServiceLoader. The core holds no language parsing and no provider code; plugins depend only on the API module; plugins do not depend on each other. Provider order is sorted by plugin id.; rationale: The optional-plugin model keeps the core small and lets a language be added or omitted without touching it, which bounds the blast radius of a plugin change and keeps discovery deterministic regardless of which plugins are present. The three boundary rules are enforced by ArchUnit (SC-003) and the sorted order by PluginLoader (SC-004).; owner: the Architect and Programmer.
- **AD-004 The human-reviewed decision is the authoritative record** — The authoritative classification of record is the human-reviewed result — the content-hash-keyed AI cache plus the override file — not the raw AI output. Overrides are applied deterministically with confidence pinned to 1.0/0.0 and take precedence over AI output.; rationale: Because AI inference is non-deterministic, the reviewed artefact is what an evidence package should rest on; re-running on the same commit with the same cache reproduces it for unchanged classes. This makes AI-influenced output reproducible for audit (CO-014).; owner: the Architect and Programmer.
- **AD-005 Frozen-contract versioning for audit and taxonomy artefacts** — The DeltaReport CSV columns, the ClassificationOverride YAML fields and the closed taxonomy are treated as frozen contracts. Changing one is a versioned, documented change — bump the schema/taxonomy version and update the README, CLI reference and audit-format docs in the same PR; columns are appended, never reordered or retyped.; rationale: Downstream compliance tooling and the GUI audit trail consume these contracts; an unversioned break would silently desync them. This is the policy PL-001 and is the rationale behind the audit/evidence and taxonomy version-control services (CO-004, CO-005).; owner: the Architect and Programmer.
- **AD-006 Grammar-compiler JARs are excluded from the distribution** — The ANTLR grammar-compiler JARs (antlr4, ST4, icu4j, antlr-runtime, treelayout) must not ship in lib/; only the antlr4-runtime is distributed. The exclusion is wired on both runtimeClasspath and guiRuntime and is re-verified after any ANTLR version bump.; rationale: Only the runtime is needed at execution time; shipping the compiler toolchain would enlarge the attack surface of the distributed artefact for no functional gain. This is a distribution-integrity decision under build-and-distribution integrity (CO-006).; owner: the Architect and Programmer.
- **AD-007 Three-tier data-residency model** — AI enrichment is offered in three residency tiers — Tier 1 local Ollama (no egress), Tier 2 operator-controlled manual prepare/consume (no egress from the scan host), and Tier 3 hosted provider over HTTPS (minimal payload) — so the adopter chooses what, if anything, leaves the host.; rationale: Regulated and air-gapped adopters have different egress constraints; offering local and manual zero-egress paths alongside the hosted path lets the tool serve strict-DLP environments while still supporting hosted inference where permitted. This realises data minimisation (CO-007) and underpins credible offline operation (CO-012).; owner: the Architect and Programmer.
- **AD-008 Keyless SLSA build provenance adopted (D-4)** — The release workflow attaches SLSA build provenance to the release artefacts using keyless attestation (GitHub OIDC + Sigstore), and the project publishes an OpenSSF Scorecard. No managed keys are used.; rationale: Keyless provenance gives consumers a way to verify that an artefact was produced by this repository's pipeline, detecting tampering during the build, without the key-management burden that D-1 declined. It is technically a signed attestation, which the owner explicitly accepted (D-4) as consistent with D-1's rationale; it strengthens build-and-distribution integrity (CO-006) and the transparency posture (CO-011) and partially mitigates EX-001.; owner: the Architect and Programmer.
- **AD-009 Per-module risk-proportionate quality floors** — Coverage and mutation floors are set per module rather than as a single global bar, sized to each module's measured state and risk. Floors are normally raised as test strength improves, but they are not strictly one-way: a floor may be deliberately reduced by owner decision when reality requires it — the root PIT mutation standard was lowered to 55% (owner decision 2026-10-15) when new compliance/evidence feature code brought the measured score below the earlier 60%.; rationale: Different modules carry different risk (the audit-trail surface is held far higher than a Swing view layer), so per-module floors target assurance where it matters. Floors are kept honest against the measured reality: they are raised when test strength grows and reduced when an owner decides a lower but still-enforced standard reflects the real risk/measurement trade-off, rather than leaving an aspirational number that fails the build. This operationalises the enforced test-quality objective (CO-009).; owner: the Architect and Programmer.
- **AD-010 SABSA library version unified onto the product version (6.1.0)** — The SABSA library, which had been numbered separately from the product and started later with its own lower sequence (last 0.3.0), is re-baselined to the product release number 6.1.0 so that the library and the product share a single version line from now on.; rationale: A separate, lower library numbering made it harder for a reader to see which product release a given architecture snapshot describes. Aligning the library onto the product version removes that ambiguity and supports a transparent, single-version trust story (CO-011). This is a deliberate one-off re-numbering — a jump to match the product — not an increment of the library's own sequence, and it changes no architecture content by itself.; owner: the Architect and Programmer.
- **AD-011 Build supports JDK 21+ (dev JDK 27, CI/CD JDK 21); Error Prone disabled on JDK 25+** — The project supports JDK 21 or later (baseline enforced at Gradle configuration time). ### Standards
- **ST-001 SHA-256 secure hash (FIPS 180-4)** — NIST FIPS 180-4 (Secure Hash Standard) : Integrity digests and content fingerprints across the product are computed with SHA-256 as specified in FIPS 180-4; no weaker digest is used where a tamper-evident binding is claimed..
- **ST-002 JAR manifest SHA-256 digest attributes** — JAR File Specification (manifest and signed-JAR digest attributes) : The build-time reference digest of each bundled helper scanner script is recorded as a SHA-256 attribute in the plugin JAR MANIFEST.MF and generated during the build, not hand-committed..
- **ST-003 Java 21 platform baseline** — Java SE 21 (Java Language and Virtual Machine Specifications) : The product builds and runs on Java 21 or later, enforced at Gradle configuration time, so the toolchain underpinning deterministic discovery and the quality gates is a fixed, known baseline..
- **ST-004 SARIF 2.1.0 static-analysis result format** — OASIS SARIF 2.1.0 (Static Analysis Results Interchange Format) : The SARIF output emitter conforms to SARIF 2.1.0; a change to the emitted structure is a versioned, documented change under the frozen-contract discipline..
- **ST-005 CycloneDX 1.5 software bill of materials** — OWASP/Ecma CycloneDX 1.5 SBOM specification : The build emits a CycloneDX 1.5 SBOM for the distributed artefacts; the SBOM schema version is pinned (VERSION_15) and changed only deliberately..
- **ST-006 CVSS v3 vulnerability severity scoring** — FIRST Common Vulnerability Scoring System v3 : Dependency vulnerabilities are scored with CVSS v3; the build fails when any runtime dependency carries a vulnerability scored 7.0 or above..
- **ST-007 SPDX licence identifiers** — SPDX Licence List (short-form identifiers) : Runtime-dependency licences are expressed as SPDX short-form identifiers and checked against the allowlist at config/allowed-licenses.json; a non-allowlisted licence fails the build..
- **ST-008 CSV and YAML audit-schema formats** — RFC 4180 (CSV) and YAML 1.1/1.2 specifications : The DeltaReport (CSV) and ClassificationOverride and overrides.yaml (YAML) audit-and-evidence artefacts use the standard CSV and YAML encodings with a declared schema version, so a breaking field change is a versioned, documented change..
- **ST-009 Coordinated vulnerability disclosure and handling (ISO/IEC 29147 + 30111)** — ISO/IEC 29147 (vulnerability disclosure) and ISO/IEC 30111 (vulnerability handling) : The disclosure channel and internal handling process follow the external-reporting and triage/remediation practices described by ISO/IEC 29147 and 30111..
- **ST-010 OpenPGP message and signature format** — OpenPGP (RFC 4880) : The published vulnerability-reporting contact supports OpenPGP-encrypted e-mail so a reporter can transmit sensitive details confidentially..
- **ST-011 SLSA build provenance (in-toto / Sigstore keyless)** — SLSA provenance, in-toto attestation format, Sigstore keyless signing : Release artefacts carry an in-toto build-provenance attestation produced by keyless Sigstore signing (no managed keys), consistent with decision D-4 and the D-1 no-managed-key boundary..
- **ST-012 OpenSSF Scorecard security health checks** — OpenSSF Scorecard : The repository runs the OpenSSF Scorecard checks in CI so its security-health posture is measured against a recognised open-source baseline, consistent with decision D-4..
